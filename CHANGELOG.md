# Changelog

## Unreleased
- **🔒 The premium tiers stay, and nothing can be bought until an operator says so: selling is now a switch, not a consequence of having a checkout link**: two URLs pasted into a host during an evening of store setup would have put a Buy button on a public page and started charging — the change that goes live without anybody deciding it. `PLAN_CHECKOUT` (committed as `0`) is that decision, held separately from the two Lemon Squeezy links for the same reason `PLAN_ENFORCEMENT` is a switch rather than an inference: configuring a store and opening it for business are two different acts. With it off, **no host shows a Buy button**, on any page, however many links are filled in — and the tiers are *not* hidden: `/pricing` still lists Free, Pro and Enterprise with their prices, features and the systems each one unlocks, describing where the project is heading rather than what it charges, with every button on the invite. The gate sits in **one place**, `plans.checkout_url`, which is where every surface that offers a plan for money already asks, so a page added later cannot leak a price by forgetting to check a switch. The on/off reading is spelled out rather than left to `bool(os.environ.get(...))`, because the empty string and the word `"0"` are both false strings an operator may write and `bool("0")` is **true** — a switch that turns itself on when somebody writes `off` is the one failure a person cannot see, so `off`, `no`, `false`, `0` and blank all read as off and `on`, `yes`, `true` and `1` as on. The CI warning follows the switch instead of nagging: it fires only in the state that is a mistake — selling switched on with no link to sell through — and stays quiet when buying is deliberately off, because a warning that appears on every push is a warning nobody reads. Committed `0` in `render.yaml` and both documented in `.env.example`, which also lost the two junk `[TEMPLATE]` placeholder lines it had been starting with.
- **💳 A plan a server can actually be on, and a Lemon Squeezy licence that proves it — plus four claims the pricing page was making that nothing could keep**: the store sells two products (Pro ₹499/mo, Enterprise ₹1,499/mo) and the page listed three tiers, and until now nothing connected the two: both paid buttons pointed at the invite page, and buying would have delivered nothing at all. `utils/plans.py` is the missing half — the plan model, and the licence. **A licence is activated per server** (`/bot plan`, administrator, one command with optional options because `/bot` is one of Discord's hundred slots), which is what makes "up to 5 servers" the *store's* rule rather than a number this bot invents and then gets wrong: Lemon Squeezy counts activations against the licence, each server keeps its own row, and releasing one here hands that activation back for somewhere else. A key for a product this deployment does not sell is valid at the store, so it is **handed straight back** rather than left spent, and the refusal names the `LEMONSQUEEZY_VARIANT_*` variable that would fix it; a network failure never downgrades a paying server, and a refused release keeps the record it could not undo, because forgetting a licence the store still counts is how the same seat gets sold twice. Validation uses the store's **public** licence API — no API key is stored and no webhook endpoint has to exist. **Enforcement ships off** (`PLAN_ENFORCEMENT=0`), deliberately: switching it on takes Support Tickets, Economy & Casino, the Market, Starboard and the Activity Tracker away from every server that has not activated a licence — including servers using them today — and holds a free server to one server and no scheduled messages. That is the operator's decision, not a side effect of wiring checkout, so the plans are recorded and displayed and the pricing page says in words that limits are not switched on yet. When it is turned on the withholding is applied in **one place** — `utils/modules.get_states`, which the command gate, the per-server command list and the dashboard all read — so a switch, a picker and a refusal cannot disagree about the same server; the dashboard's single toggle refuses in its own words rather than springing back with "could not save", and "enable all" reaches only the systems the server may have. **The page stopped selling things that do not exist.** The monthly/yearly toggle switched every price to a yearly number with a "Save 20%" badge, and both products in the store are monthly subscriptions — a price nobody could ever be charged, which is the same defect as the dead buttons this page was already rebuilt to remove, one layer further in. Prices are now the store's own (₹0 / ₹499 / ₹1,499) and come from the plan model, so the site cannot advertise a tier the code lacks; both paid cards link at the merchant of choice when the deployment has a checkout URL, and say "No billing yet" when it does not. And **four FAQ answers described a product that does not exist**, each of which reads perfectly plausible: a *7-day free trial of Pro features* on every new server (no product offers one and no code implements one); *"we're setting up our payment processors"* (stale the moment checkout is configured); *"we use encrypted backups"* — the cloud backup is a **raw SQLite file** in a private bucket, and encryption at rest was deliberately removed with the old Gist backup, so the page was contradicting the privacy policy it links to; and a *30-day* post-downgrade retention window that appears in no code path and disagrees with the policy's own 90 days for message history and 365 for activity. Each is now pinned by name in `tests/test_pages_site.py`, because the way they fail is by reading as true. One thing the docs guard caught while this was being written, and it was right to: the checkout variables were being read as `f"LEMONSQUEEZY_CHECKOUT_{plan}"`, which is a name no grep finds — so `.env.example` looked like it documented two variables nothing read. They are spelled out in `CHECKOUT_ENV`/`VARIANT_ENV` now, and the key is only ever shown masked (`38b1…4d51`). **A refusal is not an outage, and the first version of this client could not tell them apart**: the licence API answers a key it has never issued with `404` and the documented falsey body (`{"activated": false, "error": "license_key not found."}`) — measured against the real endpoint, not read off the docs — and every non-200 status was being raised as a transport failure, so a buyer who mistyped one character would have been told *"Could not reach Lemon Squeezy"* and gone to check their connection instead of their receipt. A body carrying the API's own result shape is now returned as the store's answer, while a genuine outage (a `502` and an HTML gateway page, an unreadable body) still reports itself as one. 36 new tests (**1,259 passing**), and `.env.example` plus `render.yaml` declare the four new variables with `PLAN_ENFORCEMENT` committed as `0` so the deploy has a definite state instead of a prompt.
- **🧪 The test suite had been failing on GitHub, and the harness it blamed was broken only where nobody had a database**: every `Tests` run since 09:07 was still "in progress" — fourteen of them, the oldest for seventy-six minutes — each parked at `Run test suite` with no log published and no red check, so for an hour and a half the repository looked verified while nothing was. The suite is not slow: it is **1223 tests in 15 seconds** locally, on the same committed code. What was *wrong* is more interesting than the hang, because it was found without it: reproduced the CI shape exactly — a checkout with **no `bot.db` and no `.env`** — and the suite failed two tests, `PreviewHarness.test_the_harness_refuses_what_the_real_endpoint_refuses` and `test_toggling_a_module_in_the_harness_is_reversible`. The cause is that `scripts/preview_dashboard.py` copies the operator's `bot.db` into its temp directory *if it exists*, and a fresh clone, a CI runner and any new contributor have no such file, so the pages were handed an empty SQLite file with **no tables**: `/api/toggle-all` answered `500 no such table: guild_modules`, and the harness's own logs said so (`[MODULES] ❌ Failed to save leveling=False for guild 777001`). Both tests passed on this machine only because it happens to have a populated `bot.db` — the classic shape of a suite that cannot fail in the place it is supposed to run. The fix is to build the schema from the bot's own idempotent `setup()` against the copy when there is nothing to copy, in a thread if the import ever happens inside a running loop; verified by running the whole suite in a clean checkout with neither file present, where it is now **1223 tests, OK** where it was two failures. The workflow is hardened against the *invisibility* of the other problem rather than the guess about its cause: `faulthandler.dump_traceback_later(120, exit=True)` dumps every thread's stack and fails the job if the suite blocks, `timeout-minutes: 20` bounds it from outside, and `concurrency` cancels superseded runs instead of stacking fourteen of them behind a wedged one. The next run's log names the line it is stuck on, which is the diagnostic this could not produce before.
- **🐾 The bot's status is editable now, and the line that was reported is gone**: the presence was a twelve-line tuple hardcoded in `bot.py`, so the only way to change one word was to edit the file and redeploy — and `/bot status` did not exist, which made "remove this one" a code change. The list lives in the database now (`utils/presence.py`), read fresh on every cycle, and **"Knocking over your water glass 🐾" is not in the defaults**: I pinned that with a test that names the line, because a default is exactly where a removed thing quietly comes back on a fresh install. `/bot status` shows the rotation, `text:` adds one, `type:` picks playing/watching/listening/competing, `interval:` sets the minutes, `clear:` turns the activity off entirely ("just be online" is a legitimate choice, not an error), and `reset:` restores the shipped list — one subcommand with optional options rather than five, because Discord gives an application 100 chat-input commands in total and this bot has spent that budget before. **The honest limit, said out loud in the command's own reply: a bot's presence is application-wide.** Discord has no per-server status — an activity belongs to the gateway session, so every server sees the same line at the same moment and a server administrator who could set it would be setting it for every server, last speaker winning. That is the opposite of the *member* profile (nickname, avatar, banner, bio), which Discord does store per guild and which is why `utils/identity.py` can give each server its own name and picture while this cannot; those stay on `/bot avatar` and the dashboard's identity panel. Everything that could be wrong about a value read on a loop for the life of the process is made total rather than left to raise: a hand-edited or truncated setting falls back to the defaults, one bad entry is dropped instead of invalidating the list, an out-of-range interval is clamped (a 0-minute floor is what stops the loop hammering Discord's endpoint), and a failed settings read is reported and retried rather than killing the rotation and freezing the status until the next deploy. The rotation also no longer repeats the previous line, which a plain random choice does one time in eleven and is the only repeat anybody notices. - **🔓 Signing in with Discord could hand you to somebody else's site, and the "picture for this server" panel could not accept a picture**: both were found by driving the real surfaces and asserting on what they actually emitted, and both are in the sign-in and upload paths that were added last pass. **The open redirect was a tab.** ``_safe_next`` allowed any string starting with ``/`` that did not start with ``//`` — and the *tab* is stripped when Werkzeug builds the redirect's ``Location`` header, so ``/\t/evil.example`` arrived at the browser as ``//evil.example``: the person completed Discord's sign-in **on this domain** and was then handed to a protocol-relative URL, which is the whole shape of a phishing link. A newline was worse again — the header setter refuses to write the value at all, so the callback **raised and answered 500** *after* the session had already been replaced, i.e. you were signed in and shown an error page. A backslash was the same trick one layer down, because browsers normalise it to ``/`` for http(s). Only a printable, same-site path is a path now, and both outcomes are pinned end to end: the hostile shapes are driven through the real callback (which lands on ``/servers``, not off-site) and every shape of ``next`` is checked, including the ones that must still come through (``/dashboard?guild_id=5``). **The upload was a number, not a bug in the upload code.** ``MAX_CONTENT_LENGTH`` was **16 KB for the whole app**, and Flask checks it *before* any view runs — while ``identity`` accepts images of up to **4 MB**. So a 20 KB PNG was refused by the 413 handler with *"That message is larger than the dashboard accepts (16 KB). Shorten it or split the send."* and a 48-byte one was applied; the feature that lets a server give the bot its own picture could only ever accept a file smaller than a favicon, and the refusal it got was about messages. Only the uploaded file in the suite — 46 bytes — was small enough to pass, which is why nothing caught it. The app-level cap is now the largest legitimate request and each route's real limit is applied **per request**, so the tight 16 KB still holds everywhere else (a 30 KB composer body is refused in the message's own words) while ``/api/identity`` gets a bound that two pictures fit in, with a refusal that names the upload and its size. Everything above was mutation-checked — putting the old ``_safe_next`` back fails five tests by name, and putting the single 16 KB cap back fails the two upload tests — and **1,143 tests pass on both runners** (`1,145` on `unittest` discovery), with the live dashboard re-driven in the browser afterwards: console clean, every request 200, and an 11 MB body refused as an upload rather than as a message.

Pinned by a test that every id the API hands the browser is a string, and by another that a string channel id still resolves; verified in a JavaScript engine against the JSON the running server emits — the posted body carries the exact id, where the identical pipeline with a number produced `...833500`. - **🔴 The dashboard's channel picker was empty, and reported it as "Could not load channels: Request failed (500)"**: `/api/channels` walked `guild.text_channels` **plus `guild.news_channels`** — and discord.py has no `Guild.news_channels`, because an announcement channel *is* a `TextChannel` whose type is `news` (`channel.is_news()`) rather than a class of its own. So every authenticated request raised `AttributeError` before it listed a single channel, and the composer — the one feature whose entire job is choosing a channel — could never be aimed at one. The loop now reads `guild.text_channels` alone, which already contains the announcement channels. The reason the suite was green is the more useful half of the fix: the composer's stand-in guild *defined* `news_channels`, because it was written to satisfy the production code, and a fake that agrees with a typo hides it forever. A test now asserts that each stand-in exposes only names its real discord.py counterpart exposes — it fails against the old stub with `_Guild invents ['news_channels'], which Guild does not have` — and every attribute read on a Discord object across `keep_alive.py` and `cogs/tickets.py` was swept against the installed library for the same fault, which found none.
- **🔴 A server-scoped dashboard sign-in could drive every *other* server the bot is in**: the one-time link from `/dashboard` is scoped to the server it was created in, but `dashboard()` wrote the `0` fallback of a failed lookup back into the session — so a single page load turned a scoped session into an unscoped one, and from then on it could toggle modules on any server the bot sits in and (with the new composer) post in any of their channels. The scope test now reads the scope alone, a failed lookup is never persisted, and a scoped session gets its own guild or a `400`. Verified against a stand-in gateway: a scoped link for a server the bot has left can neither read states, toggle a module, nor deliver a message `(`, and the session is left untouched.

The page an administrator opens *because* something looks wrong was the page that crashed. One helper now computes it and refuses anything non-finite, and the card reads `—` rather than pretending a missing heartbeat is a `0 ms` ping. `/api/voice-debug` had the same fault in JSON form: a bare `NaN` is not valid JSON and every browser's `JSON.parse` rejects it, so unknown latencies are `null`.
- **🔴 The market chart could never draw on any deployment, and the page blamed the CDN**: the chart's only library is loaded from unpkg with a jsdelivr fallback, and the dashboard's own `Content-Security-Policy` named neither host — `script-src 'self' 'unsafe-inline'` refused both copies, so the chart card honestly reported "the chart library could not be loaded" while the library was fine and it was our own header refusing it. Both pinned hosts are named now, and a test scans every template for external `.js` and fails if the policy forbids its origin. Verified both ways in a browser against the real header: with the old policy the console shows *Refused to load the script … script-src 'self' 'unsafe-inline'* for both CDNs, and with the fix the library loads and the chart draws.
- **🔐 On Render the dashboard had no signing key and no passkey**: `render.yaml` declared the Discord token and the backup bucket and nothing else, so `FLASK_SECRET_KEY` was regenerated on every boot — each deploy, and each wake-up from the free tier's sleep, signed the administrator out and silently killed any one-time link they were holding — and `ADMIN_PASSKEY` was unset, which disables passkey sign-in outright and left `/dashboard` in Discord (which needs the bot awake to answer) as the only way in. Both are declared now, as prompts rather than committed values. The sign-in link is also built from the URL of the process that minted the token: run from the development Mac it handed out links to the Render URL, whose process had never seen the token, which is what "that sign-in link has expired or already been used" actually was.
- **A dashboard that cannot listen says so**: if the port was already held (an older instance of the bot, typically) the server thread died inside itself and the only symptom was that the dashboard never loaded. It now names the port and the likely cause. The server shown when a session has nothing selected is also picked deterministically instead of out of a set's iteration order.
- **📣 The dashboard can post as the bot — in any channel, tagging anyone**: `/dashboard` gained a **Message composer**: pick one or more channels (up to five at once), write the message, search members and roles by name to tag them, choose a plain message or an embed with a title, and see a live preview of exactly what the bot will post before pressing Send. Everything is re-resolved against the live server rather than trusted from the browser, because a browser can send anything: a tag that is not a member or a role of *the server being written to* is dropped and named in the reply instead of pinged, a channel the bot cannot see is not offered and one it cannot post in is refused with the reason, the guild comes from the signed-in session so a server-pinned link cannot be talked into writing elsewhere, and the tags are placed in the message **content** rather than inside the embed — a mention inside an embed does not notify, which is the one thing a tag-someone feature must not get wrong. The 2000-character limit is measured with the tags included, an over-long message is refused with both numbers and the suggestion to send it as an embed, one client is capped at 30 sends a minute, and each send is reported per channel so a partial failure is never shown as a success.
- **⭐ A closed ticket now asks for a rating, and the answer goes to the log channel**: closing a ticket posts a one-to-five star prompt (with an optional comment) in the ticket channel **and DMs it to whoever opened the ticket**, because the member who closes a ticket is rarely the member who raised it. The rating is posted to the server's log channel as a card that tags **both** the opener and the staff member who claimed it, and a **thread is created on that post** so the reply can be followed up on. Two details make it hold together: the ticket row is written when it closes rather than when a star is tapped, which is what lets a rating answered from the DM still know who to tag once the ticket channel has been deleted a minute later; and the rating is a conditional `UPDATE`, so the same ticket answered twice — once in the channel, once in the DM — logs once and says it already has an answer. Who claimed a ticket is now recorded in the channel topic as well as the button label, since the topic is the only claim state that survives a restart. `/ticket setup`, `/ticket add` and `/ticket remove` are unchanged.
- **📊 Activity Tracker: per-day, per-channel message & voice time tracking**: new `/activity`, `/activity-top`, `/activity-channel` slash commands track every message sent and every voice-channel second spent, broken down by day and channel, with a 365-day rolling window. Background cleanup purges old data every 6 hours. A race condition in the periodic voice flush that could create phantom entries and double-count time has been fixed.
- **🔴 The live market page went blank and blamed nobody**: `/market/<SYMBOL>` loads its chart library from a CDN, and that one blocking `<script>` was the whole page's single point of failure — if it was blocked, slow, or still in flight when a restored tab was captured, the reference error inside `initChart()` killed the rest of the same inline script, so the price, the symbol picker, the watchlist, the period move and the what-if calculator all sat on their `—` defaults behind a permanent "Loading live prices…". The chart is now optional: quotes are fetched with a timeout, the chart script itself gets a deadline (a CDN that accepts the connection and then says nothing is a failure, not loading), the numbers are computed from the data rather than the canvas, a second CDN is tried, and a library that still will not load is **named in the chart card** instead of being drawn as an empty rectangle. Reproduced by pointing the page at a dead host — same stuck status, empty picker, empty watchlist — and re-checked both ways after the fix.
- **📎 The big-file upload feature is retired**: `/upload`, `/upload-big` and `/pin-upload-info` are gone, along with the instructions post the bot dropped into the upload channel on every boot, the `#uploads` channel binding in `/updatedb`, the dashboard card and `UPLOAD_CHANNEL_ID`. It earned its removal: `/upload` handed back an empty file.kiwi folder the member had to fill in by hand, and the host's preview of what did arrive never rendered, so "the upload finished but nothing shows" was the normal outcome rather than a bug. Members are back to Discord's own attachment limit. `cogs/uploads.py` and the four host clients (`catbox`, `file_kiwi`, `filehost`, `streamable`) are archived intact in `deleted_features/`, with restore steps in that folder's README; the `upload_channel_id` guild setting is deliberately left in the database, where nothing reads it. **The three commands are also taken out of Discord's picker**: the sync only ever upserts — that is what stops a spent write budget from clearing the guild — so a command with no local counterpart is neither missing nor stale and would otherwise sit there forever, failing for whoever clicked it. A short explicit list (`commands_sync.RETIRED_COMMANDS`) is now the only thing the sync may delete, one named command at a time, and a test pins that nothing else can vanish.
- **🔴 `/upload` stopped posting anything and told you to configure a channel**: the upload channel became `guild_settings.upload_channel_id`, then `UPLOAD_CHANNEL_ID`, then *nothing* — and with the environment variable unset every server got "❌ No upload channel is configured for this server" instead of a working command, while the sticky post in the same channel kept advertising it. The fallback is a real channel again, a setting that points at a deleted channel or another server now falls through instead of taking uploads down with it, a mistyped `UPLOAD_CHANNEL_ID` is a fallback rather than a crash at import, and the sticky post reads the same constant as `/upload`, so the two cannot disagree. There were three copies of that channel id in the tree; there is now one.
- **The sticky upload post could duplicate itself on every restart**: it looked for its own message in the last 50 messages, so as soon as the channel got busier than that it could not find the pin it had just made and posted another one. It asks for the channel's pins directly now, and only falls back to a history scan if that fails.
- **A burst of uploads could starve the database backup**: every upload holds a worker thread for up to five minutes on the same executor the backup loop uses, so fourteen concurrent `/upload` calls queued every snapshot behind them — the "my progress did not save" symptom arriving through a different door. Uploads are capped at four at once, which leaves the backup room to run.
- **🔴 The title clamp sat exactly on the boundary it was supposed to stay under**: Discord measures an embed title in UTF-16 units, so the `📎` prefix alone costs two and a "256-character" title was really 257 units — one emoji past the limit, refused with the very HTTP 400 the clamp exists to prevent. The limit is now measured the way the API measures it, which also stops a trim from slicing a surrogate pair in half and leaving a replacement character in the title. The same unit-aware rule bounds thread names, message content, and the failure card, and the sticky instructions embed is now pinned against Discord's embed limits too, since a rejected one fails silently — the only symptom is that nothing appears.
- **🔴 A long title could throw away the upload it had just paid for**: Discord rejects an embed whose title is longer than 256 characters, and `/upload` built its title straight from the member's `title` (or the attachment filename) with nothing bounding it — so `channel.send` raised *after* the bytes were already on catbox, the deferred command died with no reply, and the member got neither the link nor an error. The title is now clamped, and a rejected post is caught and answered with the link anyway, because the file is already uploaded at that point. The failure card had the same shape: a service error carrying thousands of characters pushed it past Discord's 2,000-character message limit, so the explanation was itself rejected — each reason is now one bounded line and the card is cut to fit.
- **🔴 Backups were uploading a database that was missing the newest rows**: the database runs in WAL mode, so every row committed since the last checkpoint lives in `bot.db-wal` — and the upload read the main file with a plain `open(..., 'rb')` after a **best-effort** checkpoint that quietly gives up when any other reader or writer is busy, which on a live bot is most of the time. The uploaded copy was therefore *older than the database it came from*, and the next restart restored that older state: this is what "my level and coins went backwards after a restart" is, and it is not a lost restore at all. Snapshots now go through SQLite's own backup API, which copies a transactionally consistent database including the write-ahead log, and a test commits a row, deliberately never checkpoints it, uploads, and then opens the uploaded bytes to prove the row is in them.
- **🔴 A failed restore looked exactly like an empty bucket, and then the empty database replaced the backup**: `_storage_list()` returned `[]` both when the bucket was genuinely empty and when the Supabase call itself failed — so a network blip at boot told the bot it was a brand-new server, and 25 seconds later its empty database was uploaded over everybody's progress. That is the reset. The failure is now a distinct value (`None`), the restore **retries** before giving up, and when it still cannot read the backup the instance is left **blocked from uploading** — permanently, until a restart succeeds — because an instance that could not read the only copy must never write over it. While it is still empty it keeps retrying in the background, so a container that booted during an outage heals itself instead of needing to be redeployed.
- **Only a descendant of the backup may overwrite it, and the bucket is consulted before the first write either way**: a restored instance is a legitimate heir; an instance that never restored is a stranger whose database is a different truth, and it is refused with the reason printed and shown in `/dbstatus`. That check used to depend on the startup restore having run, which is a guard with a way around it — the dashboard's own thread can ask for a backup — so the backup path now lists the bucket itself when nobody has, and being **unable to list it is not permission to write over it**. A file that will not open as SQLite is refused outright rather than treated as an empty server, which is the distinction between damage and a fresh start. A **collapse** in row counts is held back for four checks — long enough for a half-finished write or a restarting neighbour to sort itself out — and then accepted, because a server that really was reset has to be able to save again. A deliberate wipe can skip the wait with `CLOUD_SYNC_ALLOW_SHRINK=1`.
- **Two instances can no longer take turns reverting each other's progress**: the bot is run from Render *and* from a launchd agent on the development Mac, both pointing at one bucket, so whichever booted last uploaded its own idea of the database — the smaller, older one included. A **lease** object in the bucket names the host that owns the writes and is refreshed while it is alive (every two minutes idle, on every upload otherwise); another host that starts up restores the backup read-only and is told to keep its hands off until the owner has been silent for five minutes. It is deliberately advisory — an unreadable lease does not stop backups, since the descendant rule above is the one that must never fail.
- **A redeploy saves before it dies**: Render stops a container with `SIGTERM` and kills it seconds later, and a signalled Python process never reaches its `finally` block — so every coin and XP earned since the last 25-second tick was thrown away on each deploy. `main()` installs a `SIGTERM` handler that writes a final snapshot first.
- **🔴 The snapshot retention rule had never once run, and the failure was silent**: `_storage_delete` reused the shared JSON headers for a bodiless `DELETE`, and Supabase Storage answers exactly that with `400 Body cannot be empty when content-type is set to 'application/json'`. The error was read by a bare `except` and turned into `False`, which the pruner ignored — so the bucket held **15** snapshots under a documented "keep the newest 5", and every deploy added more. The request now carries no content type, a refusal is printed instead of swallowed, the prune reports how many it removed, and a test asserts the request shape itself — because the in-memory fake bucket in the suite accepted anything, which is exactly why this passed its own tests for weeks while production pruned nothing.
- **`/dbstatus` no longer stalls the whole bot while it asks**: the refusal check talks to Supabase and reads SQLite, and it ran inline in the command's coroutine — measured at **507 ms** of frozen event loop with a stand-in for the network, and the real Supabase has answered in seconds, during which no other command, no voice payout and not even the gateway heartbeat could run. It goes through `asyncio.to_thread` like the rest of that card, and a test asserts the decision is computed on a worker thread so it cannot quietly move back.
- **A server whose every backup was empty could never save again**: the restore prefers a full snapshot over an empty one, which is right, but when *all* candidates were empty it fell through to "no usable backup found" and blocked uploads **permanently** — so a brand-new deployment could bring the bot up, hand out coins, and never persist a byte. An empty backup is a worse answer than a full one, but it is still an answer: the newest empty candidate is now installed and saving resumes, with the reason logged.
- **`/dbstatus` says why an upload is not happening**: the refusal is computed by one function (`upload_refusal_reason`) that both the backup path and the card call, so the card cannot drift from the rule that is actually applied, and it names the backup it restored with the row counts it restored — the number a human needs to tell "the restore worked" from "the restore silently gave me nothing".
- **📎 `/upload` uploads the file now — it used to post a link to nothing**: the command downloaded the attachment and then only called file.kiwi's *empty folder* endpoint, which creates a folder for a human to drag a file into. The link that landed in the channel contained **no file at all**, and the failure looked like success. `/upload` now streams the bytes straight off disk to **catbox.moe** — 200 MB, no API key, permanent, and it answers range requests so Discord plays videos inline — and the message links to the file itself. Verified end to end by fetching the uploaded URL back and comparing it byte for byte with the source, including chunked (5 MB) uploads, an oversize file, an empty file, and a filename full of quotes and newlines; the body is built as an exact-`Content-Length` stream, because `http.client` would otherwise fall back to chunked transfer encoding, which catbox refuses.
- **file.io was dead weight and is out of the chain**: every upload paid a full round trip to a host that answers with an HTML page instead of a link, and then printed its failure in the member's error card. The chain is now catbox → Streamable (video, when credentials exist) → **file.kiwi** as the honest last resort, and the last-resort link says plainly that the member still has to drag the file in. A `catbox` 5xx that carries a URL in its body is treated as the success it is rather than thrown away after the bytes were already uploaded.
- **🔴 The update note could be marked as delivered without ever being sent**: the changelog hash was written to the database *after* the post attempt but unconditionally — so a missing channel, a rejected embed, or a deploy that restarted mid-announcement permanently consumed the note and no later boot ever tried again. That hash is now stored only once Discord has accepted the message, and the digest that goes into it is built for the limit rather than for the file: the newest section's entries, each cut to one readable line, capped at six entries and 3,300 characters, because an embed description over 4,096 gets a 400 — which is how "the update never showed up" happens. `tests/test_update_announcement.py` renders the **shipped** CHANGELOG through the real summarizer and fails if it stops fitting.
- **The pinned upload instructions are one embed, not two copies**: the startup sticky post and `/pin-upload-info` each carried their own hand-written text — both still advertising the dead file.io — so the channel's instructions drifted from what the bot does the moment either changed. Both now render `cogs.uploads.build_info_embed()`.
- **Supabase replaces the Gist for database persistence**: the old Gist-based backup was encrypted (NaCl), base64-encoded, and stored in a public-by-default gist — three moving parts that each had a failure mode. Supabase Storage is private by default (the service-role key is required for every read and write), so the application-layer encryption, base64 encoding, and public-gist warnings are all gone. The upload and download paths are raw binary, and the restore/backup cycle is the same: download on startup, upload every 25 seconds, hourly snapshots pruned to five. - **🐾 The Meow Fee: a small cut on coins moving between members, banked instead of burned**: sending coins (`/pay`) and the takings from a successful robbery (`/rob`) now carry **2%**, at least 1 🪙 and never more than 500 🪙, paid into **Meow Bank** — a per-server house account. The market's treat fee *leaves* the economy; this one stays in it, which is exactly why it is small: there is no inflation argument for making it bite, only the mild cost of passing coins to somebody else. Two rules keep it honest. **It is charged on top of what was promised**, so the recipient receives exactly the amount they were sent — a fee taken out of the amount would short the person who did not agree to pay it. And on a heist it comes out of the **robber's** proceeds, never the victim's, so what the victim loses is identical whether the fee is on or off.
- **The fee moves inside the transaction that moves the money**: the sender's debit, the recipient's credit and the bank's deposit all happen on one cursor inside one `BEGIN IMMEDIATE`, so coins cannot leave a wallet without reaching the bank, and a transfer can never be half-done. The switch is read *before* the transaction because it lives in another table and a transaction must not wait on a second connection. `/pay`'s balance check now compares against **amount plus fee** — it compared against the amount alone, so a sender one coin short of the fee would have been refused *after* the debit was attempted. On `/rob` the debit is still conditional on the victim still holding the loot, so a heist can't mint a coin through the fee.

- **🔴 The bot refuses to overwrite a backup it cannot read**: a changed key (or a rotated token) made the restore fail quietly, and the upload path's only protection was the "local database looks empty" heuristic — which is bypassed as soon as anyone earns a coin, at which point the fresh database was uploaded and **the one good backup was destroyed**. A failed restore for that reason is now recorded, uploads are refused while it stands, and the reason is printed with what to do about it (restore the key, or delete the old snapshot deliberately). The same guard covers a boot restore that could not reach GitHub **at all**: that process is running without everyone's progress, so it must not be the one to overwrite it — previously, one member earning a coin was enough to defeat the empty-database check. `tests/test_backup_roundtrip.py` proves the file is left byte-identical and no API call is made.
- **The first upload can no longer write to a Gist it never read**: the remote was inspected on the first upload of a deploy, but when that read *failed* (a network blip, an expired token) the code carried on and wrote anyway — the exact case where the remote could still hold a good backup. An unread remote now defers the upload to the next cycle, since the loop retries every 25 seconds. A refused `PATCH` also no longer advances the "already uploaded" hash or claims a rotated snapshot that was never stored, so the retry happens promptly instead of up to 30 minutes later.
- **The dashboard's on-demand backup can no longer race the periodic loop**: `keep_alive._schedule_cloud_backup` runs in its own thread while `cloud_sync_loop` runs every 25 seconds, and the two shared this module's "what did I last upload" state — a snapshot one thread had just written could be pruned by the other's stale view of the remote. Uploads are serialised behind a lock that skips rather than queues, and repeated warnings print once per process instead of every 25 seconds.
- **🔴 Two comparison bugs were burning the write budget on changes that never happened**: Discord returns `default_member_permissions` as a **string** (`"8"`) while discord.py sends the integer `8`, and it **strips the emoji variation selector** `U+FE0F` — so `/rps`'s `"✂️ Scissors"` is stored as `"✂ Scissors"` and `/leaderboard`'s `"🎙️ Voice Chat Time"` as `"🎙 Voice Chat Time"`. Both made those commands look permanently out of date, and because the sync re-sends whatever looks changed, **exactly those commands were re-uploaded on every boot** — forever. Verified against the live application, which reported eight gated commands plus `/rps`, `/leaderboard` and `/roulette` as changed while they were identical; the live scopes now report **`stale=0`**. `tests/test_command_sync.py` pins both payloads exactly as Discord returned them.
- **🔴 `/sync` was a second route to the wipe, and is now safe**: the slash command still called `tree.sync(guild=...)` and then `tree.sync()` — the destructive *bulk* overwrite that clears a scope's whole command list before rebuilding it — so an admin running `/sync` while the daily write limit was spent would have wiped the guild again, from inside Discord. It now goes through the same additive publisher as the boot sync (`bot.publish_commands`, reached through the bot instance because importing `bot.py` from a cog would re-execute the entry module), and reports what it published without claiming a removal that never happened. `tests/test_command_sync.py` parses the command and fails if a bulk sync or `copy_global_to` returns to it.
- **Commands are also published to Discord's global scope**: the guild lane can be closed for a whole day (`30034`) while the *global* scope has its own budget — verified live, where a guild write was refused but a global one succeeded. The boot sync now publishes missing/changed commands globally first, so every server the bot is in (and any it is invited to later) still shows them; read-compare-write means an unchanged tree costs nothing. `sync_commands` reports it under `"(global)"`, and a spent global budget is drained in the background like a guild's.
- **The background drain now has long enough to finish**: it gave up after 4 hours and passed the rest to "a restart will carry on", but nothing restarts the process on its own — so a guild that was tens of commands behind could be left part-full indefinitely. The budget is now 12 hours, which is long enough for it to actually converge at the rate the window refills.
- **🔴 Commands now register themselves — the tree had drifted to 71 of 93 and `/sync` was missing**: the bot never published its command tree on startup, and the only path that existed was the manual `/sync` slash command, which has to be registered before it can be used. The live guild was therefore stuck 22 commands behind — `/loan`, `/repay`, `/crash`, `/marry`, `/rizz` and `/sync` itself all existed in the code and simply weren't registered, so nothing anyone ran from inside Discord could bring them back. `bot.py` now syncs every guild on boot (per-guild, so a newly invited server self-heals too), and `force_sync.py` does the same from a shell without waiting for a redeploy.
- **The sync respects Discord's command-write budget**: Discord allows 200 command writes per day per guild and then answers error `30034`, after which *nothing* registers and it looks exactly like "the new command never appears". The tree is therefore compared before it is written (`utils/commands_sync.py`): a guild that already matches is left alone, and only genuinely new or changed commands cost a write. Because that budget refills a slot at a time, a guild with commands still pending is drained by a background loop that keeps publishing until it is complete (up to 4 hours), instead of needing another restart.
- **🔴 The sync can no longer delete commands**: Discord applies a *bulk* command sync destructively — it drops the guild's whole command list and then rebuilds it — so when the daily write budget ran out mid-request the deletes had already landed and the guild was left with **one** command instead of 74. Each command is now sent with its own upsert request, which can only add or replace, so a rejected request is harmless. `force_sync.py` defaults to that additive path as well; `--overwrite` re-enables the old, destructive bulk call explicitly.
- **The comparison ignores what Discord doesn't echo back**: discord.py sends `options: []`, `contexts: null`, `integration_types: null`, `required: false` and the deprecated `dm_permission` on every command, while Discord stores a default by *omitting the key*. A naive diff called every unchanged command "stale" — verified against the live guild, where 73 of 74 registered commands looked changed, which would have re-uploaded the whole tree on every boot and burned the daily budget on nothing. `tests/test_command_sync.py` pins the real payload shapes that were captured from Discord.
- **Meow Bank is a real bank now — your credit line grows with your level**: the loan system was one hardcoded rule (a flat 50,000 cap, 10% flat, a "7-day term" that nothing ever checked), so the leveling system had no effect on the economy at all. `/loan` now derives the credit line from your level (`utils/loans.py`: 5,000 base + 2,500 per level, capped at 250,000), shows your credit rating and what the next level unlocks, and lets you pick a plan — **Standard** (full line, 10%, 7 days), **Quick Cash** (5%, a third of the line, 3 days) or **Shark** (double the line, 30%, 2 days). `/repay` takes an `amount` and a `from_bank` switch, so a debt can be paid down in part and straight out of the bank.
- **A missed loan now has consequences**: the stored due date was written and then never read, so a "7-day term" meant nothing and a default was free. After a 6-hour grace period the outstanding balance takes a one-time 25% penalty (minimum 50), the loan is flagged overdue on the card, and new borrowing stays blocked until it is cleared. The penalty is applied inside the same transaction that reads the debt, guarded by a `late_fee_applied` flag, so two commands racing can only ever charge it once.
- **Borrowing and repaying are atomic**: `/loan` read "no active loan" on one connection and inserted on another, so two simultaneous calls both credited the wallet — and the loser of the race got an unhandled `IntegrityError` instead of a message; it now inserts and credits in one `BEGIN IMMEDIATE` transaction and the second caller is told they already have a loan. `/repay` debited with a plain `wallet = wallet - ?`, which *clamps at zero instead of refusing*, so two repayments could both "pay" coins that only existed once and the second cleared the loan for free; it now debits conditionally and checks the row count. `int(amount * 0.10)` also made any loan under 10 coins completely free — interest now has a floor of 1.
- **The `loans` table upgrades itself**: `/loan` gained `plan`, `status`, `taken_ts` and `late_fee_applied` columns. `CREATE TABLE IF NOT EXISTS` never alters an existing table, so a live database (and every cloud-restored copy of it) would have kept the old shape and the new commands would have failed on it; `utils/db.ensure_columns()` adds missing columns idempotently and old rows are backfilled as standard loans.
- **`/eco-admin add`, `remove` and `set` were registered but calling the wrong functions**: their handlers shared a name with the newer top-level `/addmoney`, `/removemoney` and `/setmoney` commands, and a duplicate definition in one class body silently re-binds the attribute — so the group's own implementations were unreachable dead code and the subcommands ran the top-level ones instead (which is why removing coins from a wallet ignored the admin/owner tiers). The top-level handlers are renamed with a `_cmd` suffix; a slash command's name comes from its decorator, so nothing user-facing changed and all four `/eco-admin` subcommands work again. `tests/test_static_health.py` had been failing on exactly this and is green again.
- **New funny commands**: `/beg` (spare change with a 2-minute cooldown, occasional humiliation, and a rare 100-coin whale), `/aura` (the universe rates someone, and the reading is final) and `/flex` (your net worth and, if the bank is involved, a reminder that flexing borrowed money is not a flex). `/flex` reads wallet, bank and live debt, so it is gated on both the fun and economy modules.
- **The two orphaned music tests skip instead of erroring**: `cogs/music.py` was removed but `tests/test_music*.py` stayed behind importing it, which made the suite red for reasons unrelated to any real change. They now skip with a message when the cog is absent and come straight back to life if it is restored.
- **Command budget**: with these additions the bot registers **92 top-level commands of Discord's 100 global limit** (`python -m unittest tests.test_commands` reports the tree; subcommands nest inside their parent and don't consume the budget). The 200 command-creates-per-day-per-guild ceiling is what `sync_background.py` paces, one command at a time with 429 backoff.
- **`/crash` no longer pays out after the card fails to update**: the round ran an interactive loop that edited its message every step, and on any edit failure it simply returned — with `view.ended` still false, so the **Cash Out button stayed live**. A player could then cash out at a multiplier the rocket may never have reached, while a player who did nothing lost the stake without ever getting to play. The round now ends, the buttons are cleared, and the stake is **refunded** with a "Launch Aborted" card.
- **`/crash` takes its stake atomically**: it debited with `update_wallet(-bet)`, which clamps at zero rather than refusing, so two all-in rounds that both read the same wallet could each start while only one was really paid for. It now uses `take_stake` and refuses a bet the wallet cannot cover.
- **`/sellanimals` can no longer be paid twice**: the rows were read on one connection and the coins credited on another, so two simultaneous sales of the same animals both computed a price from the same rows — the first deleted them, the second deleted nothing and was *still paid*. Read, delete and pay now happen in one `BEGIN IMMEDIATE` transaction, and the delete's row count is checked against what was read. The animals are also no longer deleted before the payment, so a failure can't cost the player both.
- **`/eco-admin remove` no longer claims coins it never removed**: it debited with `update_wallet(-amount)`, which clamps at zero, so removing 10,000 from a wallet holding 50 cheerfully reported "Removed **10,000**". It now debits exactly what is there (atomically, refusing if the wallet changed) and reports a partial removal when that is what happened.
- **The starboard's un-star path recovers from a deleted card**: it edited the card inside an `except: pass` and returned, so once a card was removed by hand or by a channel purge the row kept pointing at a dead message and the stored `stars_count` was never refreshed — the exact fault the add path had already been taught to self-heal. It now drops the stale row and re-posts, refreshes the count on a healthy card, and **keeps the row when the card itself cannot be deleted** (a missing Manage Messages permission), which used to make the next star post a duplicate beside the surviving card.
- **`/updatedb` no longer breaks other servers' logs**: it wrote the *home* server's channel IDs into whichever guild ran it, so in any other guild `log_channel_id` pointed at a channel that does not exist — and `_send_log` silently dropped every moderation action, while overwriting whatever the admins had configured. The seeded IDs are now applied only in the home guild; elsewhere it binds a local `#logs` / `#bot-cmd` if one exists, otherwise leaves the setting alone and says so.
- **Failures that used to vanish now say something**: a stale or foreign `log_channel_id` logs which case was not written, a forbidden log post is reported, and a ticket whose channel cannot be deleted tells the user instead of leaving the "deletes in 5 seconds" promise quietly broken.
- **The quote card shows the labels it was already computing**: `cat_display` and `mood_text` were built and then discarded, so a `/quote` card never said which category it came from or its mood. They are now in the footer (still plain text — no mentions).
- **Lint-level cleanup across the live tree**: six unused imports removed (`aiohttp`, `aiosqlite`, `asyncio`, `datetime`, `check_is_owner`, `dataclasses.field`), three bare `except:` clauses narrowed to the exceptions they actually expect (a bare clause also swallows `CancelledError`), two f-strings with no placeholder made plain, and several values that were computed and dropped are gone. `vc_xp`/`now` in the voice loop are *used* inside their transaction closure and were left alone.
- **A static-health test suite enforces all of it**: `tests/test_static_health.py` parses every live file and fails on undefined names, unused imports, bare `except:`, f-strings without placeholders, and duplicate definitions — using only the standard library, so there is nothing to install. `deleted_features/` is deliberately excluded, being an archive.
- **🔴 SECURITY — the dashboard no longer ships a default passkey.** `ADMIN_PASSKEY` fell back to a hardcoded string, so anyone who read this repository could sign in to any deployment that never set the variable — and `/api/set-module` accepted the same passkey with **no session and no CSRF token**, letting a stranger turn modules off in any guild. The value is now taken verbatim from the environment; when it is unset the passkey is empty, which disables passkey login and every passkey endpoint while the `/dashboard` one-time link keeps working. **If you were running with the old default, treat it as leaked and set `ADMIN_PASSKEY`.**
- **Casino bets can no longer pledge the same coins twice**: `/slots`, `/coinflip`, `/dice`, `/rps`, `/roulette` and `/gamble` read a balance and then applied a *net delta*, relying on `MAX(0, wallet + ?)`. That clamp is asymmetric — a loss could only take what you had, while a win paid in full — so several simultaneous invocations could wager the same coins repeatedly and keep every win. Every bet now goes through `settle_bet()`, which debits the stake conditionally and credits the payout inside one transaction; a bet that can't be backed is refused instead of being played for free. `/blackjack`, `/mines`, `/highlow` and `/tictactoe` now hold their stake the same way (`take_stake`), where a plain debit merely clamped at zero.
- **A timed-out blackjack hand no longer swallows the bet**: the 45-second turn timer ended the game without settling it, so a player who was dealt in and walked away silently lost their stake with no result. The timer now plays the dealer out and pays the hand exactly like Stand, and settling twice is impossible.
- **Tic-Tac-Toe stakes move together**: the challenge was accepted by debiting both players one after the other, so if the second debit failed the match started with only one player having paid into the pot. Both wagers are now taken in a single transaction, or neither is.
- **Deferred commands that fail now answer**: the error handler only replied when the initial response was unused, so any command that deferred and then raised left the user staring at "thinking…" forever. It now falls back to a followup message.
- **Moderation case numbers match their records**: the case number shown in `/warn`, `/ban` and the mod log was `COUNT(*) + 1`, so it drifted from the stored `case_id` as soon as a row was deleted ("Case #3" could be case_id 57) and two simultaneous cases could show the same number. It is now the inserted row's real id.
- **AutoMod can't be taken down by one un-deletable message**: `message.delete()` was unguarded, so a missing Manage Messages permission in one channel raised and aborted the listener before the notice (or the rest of automod) ran. The delete and the timeout are now guarded, and an unmutable spammer logs instead of breaking the loop.
- **Voice XP is written atomically**: the per-minute VC reward re-read the row on one connection and wrote it on another, so a message arriving in the same second could overwrite the minute's XP with a stale value (and a brand-new member was inserted twice). It now runs through the shared `run_atomic` helper.
- **The starboard recovers when its card is deleted**: the DB row kept pointing at a message that no longer existed, so every later star hit the same `NotFound`, the stored count was never refreshed, and the post could never be featured again. A deleted card now drops the stale row and re-posts, while a healthy card is still edited in place (verified: no duplicates).
- **The dashboard voice-debug endpoint no longer assumes music exists**: `/api/voice-debug` read `vc._player` directly, an attribute that only the archived music cog's `VoiceClient` subclass ever set. With music retired (or restored later) the lookup would raise and the endpoint would 500. It now reads the player defensively and reports `null` instead of crashing.
- **Commands in DMs explain themselves**: most commands read `interaction.guild.id` for the wallet, level row or module toggle, so invoking one in a DM raised `AttributeError` and answered "An unexpected error occurred". A central guard now replies "This command only works inside a server" (the handful of genuinely DM-safe commands are allow-listed in `utils/features.py`).
- **Two more slow memory leaks closed**: leveling's chat-cooldown map held one entry per (guild, member) forever, and the dashboard's login-attempt map held one deque per source address forever. Both are pruned once they grow past a sensible size.
- **`/uwu` can no longer be used to ping the server**: the command echoed member-supplied text back as plain message content, so `/uwu text:@everyone` (or a role/user mention) made the *bot* send the ping. The reply now sends with `AllowedMentions.none()`.
- **Admin confirmations no longer tag their target**: `/setlevel` and `/givexp` posted public messages containing `member.mention`, pinging the member — redundantly, since a real level-up is already announced by the card in the command channel. Both now show the display name.
- **`/announce` keeps pings, deliberately**: it is the one place a ping is the point, and its text is written by an admin holding Manage Server, so it opts in to `everyone`/`users`/`roles` explicitly. Every other card remains silent by default.
- **`/serverinfo` no longer reports "Server Owner: Unknown"**: `guild.owner` is `get_member(owner_id)`, which is `None` without the Members intent — the owner simply vanished from the card. The name is now resolved through the same fallback chain as the leaderboards.
- **`/levelroles` no longer claims every role has zero members**: `role.members` is only accurate when the member cache is real, so the count is now shown only when the Members intent is enabled instead of printing a confidently wrong number.
- **Leaderboards no longer ping anyone**: Components V2 promotes card text to a `TextDisplay` component, and — unlike the legacy embeds this bot used before — mentions inside a `TextDisplay` *do* notify. Adding a name to a ranking therefore tagged every member on it just because someone ran `/leaderboard`. `send_card`, `edit_card`, `send_panel` and `edit_to_panel` now suppress mentions by default (`AllowedMentions.none()`), and the one card that should reach someone — the level-up notice — opts in to pinging that member only, never the roles they unlocked. Intentionally-notifying sends (ticket pings, AutoMod notices, marriage proposals) were already plain `channel.send`/`response.send_message` calls and are unchanged.
- **Rich list and quote cards show real names instead of raw IDs**: `/richlist` resolved names with `guild.get_member()`, which is always `None` without the Members intent (this app has it disabled), so every row fell back to `User 1006948743314149426`. The same bug hit the custom-quote submitters in `/fun`. A new `display_name()` / `display_names()` pair in `utils/style.py` resolves names through the member cache, then a REST `fetch_member` (works without the intent), then the global user — and always returns plain text, never a mention, so a list can neither leak a snowflake nor ping.
- **Restore no longer silently discards the downloaded backup**: the restore path replaced `bot.db` but left the previous `bot.db-wal` / `bot.db-shm` in place, so SQLite replayed the *old, empty* write-ahead log over the freshly restored file. The download reported success while every row disappeared — a redeploy could come up completely empty. The stale log files are now removed before the swap, and a test reproduces the exact state a killed process leaves behind.
- **Backups now snapshot through SQLite, not a raw file read**: the database runs in WAL mode, so recently committed rows can still live in `bot.db-wal`. Copying the file could therefore upload a database missing the newest progress. Uploads now use SQLite's backup API, which produces a transactionally consistent snapshot including the write-ahead log, even while the bot is writing. (A row committed only into the WAL is covered by a test.)
- **Backups and the app now share one database path**: `utils/cloud_sync.py` kept its own `DB_PATH = "bot.db"` constant. Two copies of a path can drift, and a drifting backup path means the backup uploads whatever database happens to sit at *its* idea of the path. It now resolves `utils.db.DB_PATH` at call time, and the test-suite refuses to run against any file inside the project directory.
- **Uploads fail closed instead of overwriting good backups**: the backup job now refuses to write when the Gist holds encrypted backups but `BACKUP_ENCRYPTION_KEY` is missing, and when the local database has no level or economy rows while the Gist already holds a backup (the signature of a failed restore). Previously either case could replace real progress with an empty database. It also refuses to restore a payload that isn't a valid SQLite file.
- **End-to-end backup tests (17 of them)**: a redeploy simulation covering plaintext, encrypted, and the upgrade from one to the other, plus every failure mode — corrupt newest snapshot falling back to an older good one, missing key, missing credentials, non-SQLite payload, empty-database overwrite, snapshot pruning, and the exact `restore → db.setup()` order `bot.py` uses.
- **One feature registry instead of six copies**: `utils/features.py` is now the single description of every feature. The slash-command gates (`MODULE_COMMAND_MAP`), the dashboard cards, the module allow-list, the default on/off state, the help-menu structure and the cog list (`INITIAL_COGS`) are all derived from it. Previously adding or retiring a feature meant editing six places, and any drift produced exactly the reported symptoms — a green dashboard card next to a command that says the module is off, or a toggle that appears to do nothing. `bot.py`, `keep_alive.py`, `utils/db.py` and `cogs/help.py` no longer hold their own copies, and their startup validation logs any inconsistency. This also removed a stale `/ping` entry from the always-allowed command list — no such command exists.
- **A test suite (`tests/`)**, run with `python -m unittest discover -s tests -t .`. It pins the invariants that this codebase kept breaking: the closed-form level math against brute force at every level 0–500 and its inverse, the feature registry (including a real cog-load cross-check that fails if a slash command is added without being gated, or a gate names a command that does not exist), module-state persistence and concurrency, backup encryption/integrity, atomic money moves, and the Components V2 character budget. Standard library only, so there is nothing new to install.
- **Toggles have one owner now**: `utils/modules.py` holds the only module-state cache, reader and writer. The bot and the Flask dashboard previously kept *two* caches and *two* SQLite write paths, which is how they could disagree — a disabled module kept running, or a toggle silently reverted. `keep_alive.py` no longer touches SQLite for module state at all; it calls the same code the bot does. Retired module ids found in the database are ignored rather than resurrected on the dashboard.
- **Backups are encrypted, versioned and integrity-checked**: `utils/cloud_sync.py` now encrypts the database with PyNaCl SecretBox (XSalsa20-Poly1305) when `BACKUP_ENCRYPTION_KEY` is set, stores a SHA-256 of the plaintext inside the payload and verifies it before restoring (so a corrupted or tampered snapshot is refused rather than loaded), rotates timestamped snapshots keeping the newest `BACKUP_KEEP` (default 5) for point-in-time restore, and deletes the old plaintext copy the moment encryption is enabled. Without a key it still works exactly as before, but warns loudly on every upload. PyNaCl was already a dependency.
- **Every money move goes through one helper**: `utils/db.run_atomic()` replaces the nine hand-copied `BEGIN IMMEDIATE` blocks in `cogs/economy.py`. The helper takes a callback so callers keep their conditional logic (only crediting the receiver when the debit actually matched), and any exception rolls the whole transaction back. The balance operations now run in a worker thread instead of blocking the event loop.
- **One app-command error handler instead of two**: `bot.py` registered an error handler with `@bot.tree.error` *and* overwrote `bot.tree.on_error` in `on_ready`, so one of them was dead depending on timing. There is now a single handler, and an optional `ERROR_WEBHOOK_URL` forwards unhandled command errors somewhere visible instead of only printing them.
- **Level-up cards are confined to the command channel**: `handle_level_up` used to walk a five-step fallback (configured channel → hardcoded #bot-cmd → any channel whose *name* contained "cmd" → the server system channel → the channel the member was chatting in), which scattered level-up spam across the server. It now posts to the channel chosen with `/levelsettings`, else #bot-cmd, and if neither exists it posts nothing at all. The `bot_cmd_channel_id` setting that `/updatedb` wrote but nothing ever read is now honoured, so the target channel is configurable rather than hardcoded.
- **`/rob` stakes are now symmetric**: the take and the penalty come from the same roll, so it's no longer "risk a flat 100–300, win up to 50,000". A 2,000 🪙 attempt now costs a 200 🪙 fine if you're caught (10% of what you went for), the fine is capped at what you actually hold, and the card shows both the take and the risk. Tuning lives in `ROB_SUCCESS_CHANCE` / `ROB_FINE_RATIO` / `ROB_MIN_FINE` / `ROB_MAX_TAKE`.
- **Cooldowns on the free-money luck commands**: `/rob` (30 min), `/hunt` (10 min) and `/trivia` (3 min) previously had none, so they could be farmed indefinitely — `/trivia` paid 150–350 coins per correct answer with no limit at all. Bet-based casino games are left alone, since you risk your own coins there.
- **Humanised cooldown messages**: the global handler now reports "30m 0s" instead of "1800.00s".
- **Economy can no longer be duplicated**: `/pay`, `/deposit`, `/withdraw`, `/buy` and `/rob` read a balance, then wrote it back with no transaction, so two of them fired at once both passed the check — minting coins, driving the wallet/bank negative, or handing out two items for one payment. Each is now a `BEGIN IMMEDIATE` transaction with a conditional `WHERE wallet >= ?` guard and a row-count check.
- **Cooldowns can't be double-claimed**: `/daily`, `/weekly` and `/work` used the same read-then-write pattern, so two simultaneous claims paid out twice. They now use an optimistic single-statement claim that only fires if the stored timestamp is unchanged.
- **Starboard reacts to un-starring**: only `on_raw_reaction_add` existed, so a card's star count could only climb and a featured post could never come down. Added `on_raw_reaction_remove`, which re-syncs the count and retires the card (and its DB row) when it drops below the threshold.
- **AutoMod no longer leaks memory**: the per-user message log kept one entry per member forever; it now prunes quiet users and has a hard 5000-entry ceiling.
- **Leveling can no longer be inflated**: `utils/levels.py` now owns the XP/level math with a hard `MAX_LEVEL` ceiling, and `/setlevel` / `/givexp` are capped to it. Previously they accepted anything, which is how the server ended up with a Level 1351 rank-up card and a 2.4-billion-XP leaderboard entry. A one-time guarded repair re-derives every stored level from its XP and clamps out-of-range rows.
- **Leveling math is now O(1)**: the level lookup used to loop once per level (and `total_xp_for_level` summed the whole series in Python) on every message; both are now closed-form, so a high-level member no longer slows message handling.
- **Text XP / message counts no longer silently lose data**: message XP now uses a `BEGIN IMMEDIATE` transaction, so two messages arriving together can't both read the same old XP and drop one.
- **Leveling survives legacy NULL settings**: `get_guild_settings` coerced nullable columns, where `None >= 10` would previously raise and kill the whole reward path for that guild.
- **Privileged intents are now explicit and safe**: `ENABLE_MESSAGE_CONTENT_INTENT` / `ENABLE_MEMBERS_INTENT` (default off) let you opt in *after* enabling them in the Developer Portal. The app currently has neither enabled, so message text is invisible — that made AutoMod invite filtering a no-op and award XP at the baseline rate. Text XP now falls back to the standard rate instead of awarding nothing, starboard falls back to a readable description, and a clear log line explains how to enable the intents.
- **Archived six fragile features**: Music & Radio, TempVoice (Join-to-Create), Welcome/Goodbye, Color Studio & Roles, Giveaway System and Reaction Roles are removed from the running bot. Their code moved to `deleted_features/` (kept intact, never imported) along with the music-only `utils/spotify.py` + `utils/card.py` and the `yt-dlp`/`imageio-ffmpeg` dependencies. Dashboard cards, help categories, command-map entries and docs were cleaned up. Their SQLite tables were intentionally left in place so no stored data is dropped.
- **Module toggles actually stick**: The web dashboard now writes the change to the database *before* updating memory and reports a real failure instead of silently claiming success, and every toggle triggers an immediate cloud backup so a restart can't restore an older snapshot and revert it.
- **Fixed modules running while disabled, or not running while enabled**: SQLite now runs in WAL mode with a 15s busy timeout, ending the lock contention between the web thread and the bot thread. Previously a failed read made `is_module_enabled` fall back to `True` (so a disabled module kept running) and a failed write silently dropped the toggle. Reads and writes now fail loudly and retry instead of silently guessing.
- **Shared module defaults**: `DEFAULT_DISABLED_MODULES` in `utils/db.py` is the single source of truth for default state, used by both the bot and the dashboard so they can never disagree. **Giveaway, Color Studio & Roles, and TempVoice now default to OFF** (alongside Welcome). A one-time migration applies this to guilds that had an old saved value.
- **Disabled means disabled**: the giveaway background loop and entry button, and the color palette dropdown, now honour their module toggle (view callbacks previously bypassed the cog checks).
- **Components V2 message system**: Added a full Components V2 design system to `utils/style.py` — semantic cards (`success`/`error`/`info`/`warn`), a rich `card()` builder with fields, thumbnail, media gallery and footer, `progress_bar()` for XP/cooldowns, and an `embed_to_layout()` converter that upgrades any legacy embed into a container card. Text is clamped to Discord's 4000-character / 40-component V2 limits, and every helper falls back to the original embed if conversion or sending fails, so no command can break.
- **Migrated 98 messages to Components V2** across 13 cogs (economy, games, moderation, music, leveling, fun, social, server_control, starboard, colors, legal, tempvoice, tickets) via `send_card`/`edit_card`. Interactive panels that carry button/menu views are intentionally left on the legacy path for now, since merging a legacy View into a layout would drop its timeout and `interaction_check` guards.
- **Security — credentials**: Removed a hardcoded (obfuscated) GitHub token and the default Gist ID from `utils/cloud_sync.py`. Cloud backup now requires `GITHUB_BACKUP_TOKEN` and `GIST_BACKUP_ID` from the environment, and warns if the backup Gist is public. **The exposed token must be revoked and reissued.**
- **Security — login rate limiting**: `X-Forwarded-For` is now only trusted when actually behind a proxy, closing a rate-limit bypass that allowed unlimited passkey guesses.
- **Security — sign-out**: `/logout` now requires a CSRF-validated POST instead of a GET link that any site could trigger.
- **Dashboard UX**: Toasts show human-readable module names, and an expired session now redirects back to sign-in instead of silently failing.
